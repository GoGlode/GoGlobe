# Как использовать API контракты GoGlobe в проекте

Рабочая версия: 0.3, 20 октября 2026. Все файлы этой версии должны обновляться вместе. Это спецификация и моки, а не готовое приложение.

## Состав комплекта

- PDF объясняет пользовательские сценарии, состояния, сроки хранения, доступ, цены и правила повторов. Последние три раздела содержат новые исправления и инструкцию команды.
- `GoGlobe_openapi_v0.3.json` задаёт точные пути, методы, схемы запросов и ответов. Его можно импортировать в совместимый просмотрщик OpenAPI или инструмент API-разработки. При генерации типов/клиента убедитесь, что инструмент поддерживает OpenAPI 3.1 и JSON Schema 2020-12.
- `GoGlobe_examples_v0.3.json` содержит именованные записи `{schema, value}`. Для ответа мока берите объект **value**, а не весь файл или оболочку с полем schema. Моки разных состояний — альтернативы, не последовательная история одного сервера.
- `validate_contract_v0.3.py` проверяет OpenAPI, примеры, ряд бизнес-инвариантов и регрессионные случаи. `requirements.txt` фиксирует его зависимости. Сам backend этот скрипт не тестирует.

## Что исправлено после повторной проверки

1. Ответ продолжения поиска теперь имеет revision больше expected_revision. У создания и продолжения разные примеры.
2. У восстановленной по ключу сессии recovery_enabled=true.
3. Тарифные выдачи содержат context с фактическим составом и датами. Смена состава инвалидирует обе старые выдачи, смена города отправления — перелёты. Новые параметры не подписываются под старыми ценами.
4. requested_components явно задаёт объём задачи; incomplete отличает полезный частичный ответ. Сочетание empty + failed без готовых вариантов считается failed, а не успешным пустым результатом.
5. Завершённый Snapshot фиксируется. Его trip_id не обнуляется после удаления Trip; приватный GET Trip тогда отвечает 404. У строки истории ссылка может стать null.
6. QuoteRequest требует stay только для отелей и flight_dates только для перелётов. Даты Schedule/Card и координаты Place не могут быть наполовину заполненными.
7. После отмены, таймаута и рестарта компоненты не остаются в processing. Сохранённый вопрос переживает рестарт.
8. Повторное удаление уже снятого флага не продлевает TTL. Несколько GET не считаются единой атомарной операцией: клиент сверяет revision. Списки карточек TripList имеют общий sources для source_ids оценок цены.

## Распределение работы

| Участник | Работа с контрактом | Первый проверяемый результат |
|---|---|---|
| Backend №1 | API, Owner/session, хранение Trip, валидация, права, идемпотентность, сроки, тарифные адаптеры | Session → создание задачи → чтение Snapshot/Trip → Save → список My Trips |
| Backend №2 | Извлечение параметров, itinerary, вопросы, события run_id, проверка источников | Валидная программа по дням с suggested/verified и без придуманных цен |
| Frontend №1 | Home, запросы, SSE/polling, вопросы, ошибки и повторы | Все состояния генерации работают на моках |
| Frontend №2 | Trip Details, Save/Favorite, календарь, тарифные вкладки, история и Share | Поездка сохраняется и открывается по своему trip_id |
| Дизайнер | Состояния без дат, blocked/empty/failed, offline, подтверждения, восстановление | Каждому состоянию API соответствует понятный экран |

Сначала положите согласованный комплект в репозиторий, например в `docs/api/v0.3`. Не смешивайте поля редакций 0.1, 0.2 и 0.3. Если прежний API уже опубликован, несовместимые изменения выпускаются через новую версию или согласованную миграцию.

## Как фронтенду начать до готовности сервера

Сделайте отдельный слой запросов с теми же методами, которые будут вызывать настоящий API. В режиме моков этот слой возвращает `value` нужной фикстуры. Для Home используйте `accepted`, затем `state_processing`, `state_needs_clarification`, `completed_partial` или `state_failed`. Для Trip — `trip_relative`, для календаря — `trip_scheduled` и `calendar`; для тарифов — `hotel_offers`, `hotel_partial`, `hotel_empty`, `hotel_failed` и соответствующие flight-варианты.

После готовности сервера заменяется реализация транспорта. Компоненты экранов продолжают работать с теми же схемами. Слепая замена fetch на любой похожий JSON не подходит: null, единицы денег и статусы должны совпадать.

## Первый совместный сценарий

1. POST `/api/v1/session` с `{}`. Браузер получает cookie; хранить её значение вручную в localStorage не нужно.
2. POST `/api/v1/searches` с PlanRequest и новым UUID в Idempotency-Key. Сохранить выданные search_id и trip_id. После сетевого обрыва повторить этот же запрос с **тем же** ключом.
3. Читать Snapshot через GET или SSE. Вопрос отправить с его question_id и актуальной revision **задачи**. Получив готовый маршрут, открыть GET Trip.
4. PUT `/trips/{trip_id}/saved` с `{}`. Только подтверждённый ответ означает сохранение. GET `/trips?saved=true` показывает недатированную поездку в группе «Без дат».
5. Назначить schedule с актуальной revision **поездки**. Длительность должна совпадать с числом дней программы. Проверить календарь по пересечению from/to, загрузив все страницы диапазона.
6. По явному действию пользователя отправить quote-search с гостями, origin при необходимости, stay/flight_dates для выбранных компонентов. Не приравнивать автоматически дни вылета к check-in/check-out.
7. В тарифной вкладке показать даты и состав из context. При изменении параметров не отображать прежние цены как новые. quoted означает найденный тариф, а не бронь.
8. Проверить историю, Favorite, безопасный Share и скачивание recovery_key. После DELETE session восстановление ключом возвращает доступ тому же владельцу.

В v0.3 `completed/partial` для плана с готовой программой и заблокированными тарифами — нормальный полезный результат. Не показывайте вместо маршрута общий экран ошибки. Ошибка поиска тарифов также не удаляет программу.

## Как бэкенду использовать схемы

Сервер проверяет тела запросов по OpenAPI, но отдельно обеспечивает бизнес-правила: даты, фактические зоны, привязку цены к составу, сроки, транзакции и права. Схема не заменяет проверки нескольких запросов в гонке. Результат AI также проходит валидацию, прежде чем попасть во frontend.

Храните задачу и её попытку отдельно от поездки. Search.revision и Trip.revision нельзя подставлять друг вместо друга. После таймаута/cancel поздний worker с прежним run_id не получает право записать результат. Флаги saved/favorite обновляются отдельно, чтобы worker не перезаписал их старым объектом Trip.

## Локальная проверка комплекта

В распакованном комплекте, при наличии Python:

```powershell
python -m pip install -r requirements.txt
python validate_contract_v0.3.py
```

Для окружения с другим именем Python используйте его команду. Скрипт не требует ключей провайдеров и не отправляет запросы в ваш сервер.

На момент подготовки прошли: OpenAPI для 27 операций и 50 схем; 41 фикстура; 22 встроенных примера ответов; отклонение 15 намеренно неправильных объектов; 8 сочетаний итоговых состояний; 4 проверки связанных ответов. Это не нагрузочный тест и не интеграционная приёмка backend.

## Как согласовывать изменения

Нужен новый сценарий → описать его → изменить OpenAPI → обновить полные моки → проверить комплект → обновить PDF и реализацию. Ревью проводят разработчик API и тот, кто использует соответствующий ответ во frontend. Изменение enum, единиц цены, смысла Save или удаления нельзя считать косметическим.

Перед демонстрацией прогоните реальные Home → Trip → Save → Calendar, вопрос/ответ, отказ источника, повтор после обрыва, восстановление доступа, отзыв Share и удаление поездки. Поставщики, их квоты и правила хранения фотографий/тарифов ещё должны быть подтверждены при интеграции.
