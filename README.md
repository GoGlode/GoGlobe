# 🌍 GoGlobe

**One request. A trip that makes sense.**
AI-сервис для подбора путешествий по одному запросу: ИИ разбирает пожелания, находит перелёты и отели, проверяет бюджет и даты, ранжирует варианты и объясняет, почему они подходят.

> О! Хакатон 2026, трек «О!дин запрос». Онлайн 23–30 октября, **сдача до 29 октября 10:00 МСК**.
> Полная архитектура и роадмап: [`docs/GoGlobe_architecture_roadmap.pdf`](docs/GoGlobe_architecture_roadmap.pdf).

---

## 1. Быстрый старт

Нужно: Python ≥ 3.11, Node ≥ 20, git.

```bash
git clone https://github.com/GoGlode/GoGlobe.git && cd GoGlobe
cp .env.example .env
make setup        # venv + pip install (backend), npm install (frontend)
make dev          # backend :8000, frontend :5173
make test         # pytest + сборка фронта
```

- Swagger backend: http://localhost:8000/docs
- Без `make`: `cd backend && uvicorn app.main:app --reload` и `cd frontend && npm run dev`
- Docker: `docker compose up`

Из коробки уже работает **сквозной сценарий на моках**: ввод запроса → статусы поиска (SSE) → карточки → страница деталей. Дальше команда заменяет моки реальными данными, не ломая контракт.

## 2. Утверждённый стек

| Слой | Выбор | Почему |
|---|---|---|
| Frontend | **React 18 + TypeScript + Vite + React Router** | быстрый старт, один тулчейн на двух разработчиков |
| Стили | CSS + дизайн-токены (`frontend/src/design/tokens.css`) | токены отдаёт дизайнер, без тяжёлых UI-кит |
| Backend / BFF / агент | **Python 3.11+ + FastAPI + Pydantic v2** | async, SSE, типизированные схемы, лучшая экосистема для LLM |
| Контракт API | Pydantic-схемы → OpenAPI (`/openapi.json`) + зеркало `frontend/src/api/types.ts` | единый источник правды |
| Статусы поиска | **SSE** (`GET /api/search/{id}/events`) | проще WebSocket, достаточно для прогресса |
| Кэш и хранилище | In-memory TTL (`backend/app/cache`) → при необходимости SQLite | на 8 дней хватает; интерфейс не меняется |
| LLM | провайдер выбирается Backend №2 (ключ — `LLM_API_KEY`), за интерфейсом парсера | уточнить у организаторов ограничения по моделям |
| Тесты / линт | pytest, ruff, `tsc --noEmit` | запускаются в CI на каждый PR |
| CI | GitHub Actions (`.github/workflows/ci.yml`) | |

Изменить стек можно только решением всей команды в общем чате до **22 октября**; после — заморозка.

## 3. Структура репозитория

```
backend/
  app/
    api/            # HTTP-слой, роуты, SSE                     ← Backend №1
    schemas/        # контракт v0 (search.py) + формат провайдеров ← Backend №1
    integrations/   # интерфейсы провайдеров, адаптеры, mock/    ← Backend №1
    cache/          # кэш, хранилище результатов, шина событий   ← Backend №1
    agent/          # оркестратор, парсер, tools, валидация,
                    # ранжирование, объяснения                   ← Backend №2
  tests/            # сквозной тест демо-запроса на моках
frontend/src/
  api/              # types.ts (контракт), client.ts              ← Frontend №1
  state/            # состояние поиска                            ← Frontend №1
  pages/            # HomePage, ResultsPage, OfferPage
  components/       # QueryForm, ProgressSteps (FE1); OfferCard, States (FE2)
  design/           # tokens.css, global.css                      ← Дизайнер
design/             # макеты, ассеты, handoff-заметки             ← Дизайнер
docs/               # контракт, демо-сценарий, роадмап
```

## 4. Команда и зоны ответственности

| Роль | Ветка | Зона |
|---|---|---|
| **Frontend №1** | `dev/frontend-1` | каркас WebApp, роутинг, ввод запроса, форма параметров, экран ожидания, ошибки, адаптив, `api/client.ts` |
| **Frontend №2** | `dev/frontend-2` | карточки результатов, страница деталей, фильтры/сортировка, избранное/шаринг, пустые состояния |
| **Дизайнер** | `design/*` (по задаче) | макеты ключевых экранов, дизайн-система v0, токены, ассеты, питч-дек |
| **Backend №1** | `dev/backend-1` | API/BFF, схемы, внешние API и адаптеры, таймауты/повторы, кэш, запасные данные для демо |
| **Backend №2** | `dev/backend-2` | AI-агент: разбор запроса, оркестрация инструментов, валидация бюджета, ранжирование, объяснения, тесты на демо-запросах |

Ветки `feat/ai-layer` и `feature/algorithm` были созданы до этого и совпадают с `main`; оставлены как есть — Backend №2 может использовать их как рабочие под-ветки или удалить.

Сквозные зоны (один ответственный): дизайн-система — Дизайнер; **API-контракт — Backend №1**; сборка демо — все пятеро.

## 5. Работа с git

- `main` — всегда рабочая, **защищённая** (включить в Settings → Branches: PR обязателен, 1 approve, зелёный CI, запрет force-push).
- Каждый работает в своей ветке `dev/<роль>`; ежедневно `git fetch && git rebase origin/main`.
- В `main` — **мелкие PR** (≤ ~300 строк) и быстрый ревью (в течение нескольких часов). Ревьюер — разработчик из смежной зоны (FE1↔FE2, BE1↔BE2, FE↔BE1).
- Коммиты: `feat: …`, `fix: …`, `docs: …`, `chore: …`, `test: …`; области — по желанию `feat(agent): …`.
- Секреты **никогда** не коммитим: только `.env` (в `.gitignore`), шаблон — `.env.example`.
- Владельцы файлов — `.github/CODEOWNERS` (заполнить GitHub-логинами).

## 6. API-контракт v0

Единственный способ общения frontend ↔ backend. Подробности: [`docs/api-contract.md`](docs/api-contract.md).

- `POST /api/search` — `{ query, params?, search_id? }` → `{ search_id, status, parsed, clarifying_question, offers[], warnings[] }`
- `GET /api/search/{id}/events` — SSE `{ stage, message }`, стадии: `parsing → flights → hotels → validating → ranking → done`
- `GET /api/search/{id}` — сохранённый результат
- `status`: `ok | needs_clarification | partial | empty | error` — дизайнер рисует все пять состояний.
- Правило: **контракт меняется только через общий чат + PR с меткой `contract`**, который правит `schemas/search.py`, `api/types.ts` и `docs/api-contract.md` вместе.
- Отличие от PDF-черновика: `search_id` может прислать клиент, чтобы открыть SSE *до* завершения POST.

## 7. Принципы разработки (из архитектуры)

1. **Честность данных:** цены, наличие и характеристики берутся *только* из ответов инструментов. Нет данных → `warnings` / `needs_clarification`, а не догадка.
2. **Объяснимость:** у каждого варианта есть `why / pros / cons / sources / confidence`.
3. **Один рабочий сценарий важнее десяти экранов.**
4. **Запасной вариант для демо:** любой внешний источник может упасть — фолбэк на кэш/снимки с пометкой даты (`data_freshness`).
5. Не хватает параметра → уточняющий вопрос, а не угадывание.

## 11. Риски → что делаем

| Риск | Реакция |
|---|---|
| Нет API или данных без цен/наличия | BE1 проверяет до 22 окт; запасной вариант — сохранённые реальные ответы с датой |
| ИИ выдумывает цены | Данные только из tools; строгая структура; валидация |
| Медленные модель/API | SSE-статусы, таймауты и повторы, кэш, прогретые демо-запросы |
| Части не склеиваются | Контракт v0 + моки с обеих сторон + ежедневный сквозной прогон |
| Слишком большой объём | Только ключевые экраны; заморозка вечером 27 окт |
| Сбой на демо | Демо-видео, заготовленные запросы, репетиция 28 окт |
